# マインスイーパー 要件定義書

Nov 14, 2026

Claude Codeに渡す指示書です。昔のWindows風の基本的なマインスイーパーを、TypeScriptの静的サイトとして段階的に作り、GitHub Pagesで公開します。各段階の終わりに人間がレビューし、承認するまで次へ進みません。

## 1. 目的と役割

このプロジェクトの第一の目的は、Claude Codeを使った開発の進め方を練習することです。動くゲームを作ることは手段であり、過程を人間が理解できることを完成の速さより優先します。

- **人間（リポジトリの所有者）**：最終意思決定者。各段階の成果物をレビューし、次へ進むかを決める。コードを自分で書き直すとは限らないが、内容は理解したい。TypeScriptの経験あり。
- **Claude Code**：実装担当。作業の目的と判断理由を、意思決定者が判断できる形で説明する責任を負う。

迷ったときの優先順位は次のとおりです。

1. 人間が理解し、判断できること
2. 安全であること（8章）
3. 単純であること
4. 機能が多いこと

この文書に書かれていない判断が必要になったら、推測で進めずに質問してください。

## 2. 初期スコープ

作るのは基本的なマインスイーパーだけです。ここにない機能は、良い案に思えても実装せず、提案としてPRの説明に書いてください。

**作るもの**

- 難易度3種類：初級（9×9・機雷10）、中級（16×16・機雷40）、上級（30×16・機雷99）
- 左クリックでマスを開く。機雷のないマスが連続する部分は自動で開く
- 右クリックで旗を立てる・外す
- 最初に開くマスには機雷を置かない
- 残り機雷数のカウンター（機雷数 − 旗の数）
- 経過秒のタイマー（最初のマスを開いた時点で開始、上限999）
- リセットボタン、難易度の切り替え
- 勝敗の判定と表示。負けたときは全機雷と、誤って立てた旗を表示する

**作らないもの**

- カスタム盤面、ベストタイムの保存、統計、リプレイ
- スマホ向けの操作（長押しなど）。PCで快適に遊べることだけを保証する
- サーバー、ログイン、ランキング、通信を伴う機能すべて
- 効果音、アニメーション演出

## 3. 技術構成と動作環境

サーバーを持たない静的サイトとして作ります。ビルド結果はHTML・CSS・JavaScriptのファイルだけです。

| 項目 | 採用 | 補足 |
| --- | --- | --- |
| 言語 | TypeScript（strictモード） | `any` は原則使わない |
| ビルド | Vite | 開発サーバーと本番ビルドの両方に使う |
| 実行環境（開発時） | Node.jsの最新LTS | 採用したバージョンをリポジトリに記録する |
| パッケージ管理 | npm | ロックファイルをコミットする |
| UIフレームワーク | なし | 素のDOM操作とCSSで作る |
| テスト | Vitest | 対象はゲームロジック。画面の自動テストは不要 |
| 静的解析 | ESLint、Prettier | 設定は標準的なものでよい |
| CIとデプロイ | GitHub Actions | PRでテストとLint、mainでPagesへデプロイ |
| 公開先 | GitHub Pages | 公開リポジトリから配信する |
| 対応ブラウザ | Chrome、Edge、Firefox、Safariの最新版 | PCのマウス操作が前提 |
| 開発OS | WindowsとmacOSの両方 | OSに依存するスクリプトやパスの書き方を避ける |

依存パッケージは上の表に必要なものだけにします。追加したい場合は、理由を添えて事前に承認を求めてください。実行時に読み込むライブラリは0個を目標とします。

## 4. 設計方針

ゲームロジックと画面描画を別のモジュールに分けます。将来の拡張や、別のブラウザアプリを作るときに同じ型を使い回すためです。

**ロジック層**

- 盤面の状態と操作（開く、旗、勝敗判定）を持つ
- DOM、`window`、タイマーに触れない。Node.js上で単体テストできること
- 乱数は外から注入できるようにし、テストでは機雷の配置を固定できること
- 盤面サイズと機雷数は引数で受け取る。難易度3種類をロジックに埋め込まない

**描画層**

- ロジック層の状態を受け取って画面に反映し、クリックをロジック層の操作に変換するだけにする
- ゲームのルールを描画層に書かない

**見た目**

- 昔のWindows風にする。グレーの立体的なマス、くぼんだ枠、デジタル数字風のカウンター
- すべてCSSと自作のSVGで描く。既存製品の画像、アイコン、フォント、ロゴ、名称は使わない
- 外部からフォントや画像を読み込まない

ファイル構成の具体案は段階0で提案し、承認を受けてから確定してください。

## 5. 開発の進め方

4つの段階に分け、1段階ずつ人間の承認を得て進めます。複数の段階をまとめて実装しないでください。

| 段階 | ブランチ | 作るもの | 人間がレビューで決めること |
| --- | --- | --- | --- |
| 0. 土台 | `phase-0/setup` | ViteとTypeScriptの雛形、ESLint、Prettier、Vitest、PR時のテストとLintのCI、CLAUDE.md、規約文書、README | ファイル構成と規約はこれでよいか |
| 1. ロジック | `phase-1/game-logic` | ゲームロジックと単体テスト。画面は作らない | ルールの解釈とデータの持ち方は妥当か |
| 2. 画面 | `phase-2/ui` | Windows風の画面とマウス操作。ローカルで遊べる状態 | 見た目と操作感は期待どおりか |
| 3. 公開 | `phase-3/deploy` | mainへのマージでGitHub Pagesに自動デプロイする仕組み | 公開してよい状態か（8章の確認を含む） |

**1段階の流れ**

1. 着手前に、その段階の計画を提示する。作るもの、ファイル、判断が分かれそうな点を書く
2. 人間が計画を承認してから実装を始める
3. 実装後、テスト、Lint、ビルドが通ることを自分で確認する
4. 段階レポート（7章）を書き、PRを作成して作業を止める
5. 人間がレビューする。指摘は同じブランチで修正する
6. 人間がマージする。Claude Codeはマージしない
7. 次の段階の開始指示を待つ

**承認なしに行わないこと**

- mainブランチへの直接コミット、PRのマージ、強制プッシュ
- 依存パッケージの追加
- スコープ外の機能の実装
- リポジトリ設定の変更。Pagesの有効化など、設定画面での操作は手順を示して人間に依頼する

段階3の完了をもって初期スコープは終わりです。

## 6. Git運用

段階ごとにブランチを1本切り、PRを1本出します。レビューする人間が差分を追えることが基準です。

**ブランチ**

- 最新のmainから5章の表の名前で切る
- 1ブランチには1段階の変更だけを入れる

**コミット**

- 1コミットは「ひとことで説明できる1つの変更」にする。例：機雷配置の実装とそのテストで1コミット
- 設定の変更、実装、リファクタリング、文書の更新を同じコミットに混ぜない
- 各コミットの時点でビルドとテストが通る状態を保つ
- 「作業中」「修正」のような内容の分からないコミットを残さない
- メッセージの書式は段階0で規約として提案する。何を変えたかに加え、自明でない場合は理由も書く

**PR**

説明文には次の項目を入れます。段階0でPRテンプレートとして用意してください。

- この段階の目的
- 変更の概要と、読む順番のおすすめ
- 人間に判断してほしい点
- 動作確認の手順と、自分で確認した結果
- セキュリティ確認（8章のチェックリスト）の結果
- スコープ外だが気づいたこと、提案

## 7. ドキュメントと規約

規約と学習用の記録は、すべてリポジトリ内のMarkdownファイルに集約します。会話の中だけで決まったルールを残さないでください。

| ファイル | 内容 | 作る段階 |
| --- | --- | --- |
| `CLAUDE.md` | Claude Codeが毎回読む入口。ビルド・テスト・Lintのコマンドと、下記文書への参照 | 0 |
| `docs/requirements.md` | この要件定義書の写し | 0 |
| `docs/conventions.md` | コーディング規約、命名、コメント方針、Git運用、セキュリティ方針 | 0 |
| `docs/architecture.md` | ファイル構成、層の分け方、そうした理由 | 0で作成、以降更新 |
| `docs/phases/phase-N.md` | 段階レポート（下記） | 各段階 |
| `README.md` | プロジェクトの概要、動かし方、公開URL | 0で作成、以降更新 |

**規約の扱い**

- 規約の本文は `docs/conventions.md` だけに書く。`CLAUDE.md` やPRには転記せず、参照する
- 内容は段階0でClaude Codeが起案し、人間が承認して確定する
- 規約を変えるときは、コードより先に文書を直す
- この要件定義書と規約が食い違う場合は、要件定義書を優先し、食い違いを報告する

**段階レポート**

最終意思決定者が「承認してよいか」を判断するための文書です。作業ログではなく、目的と判断を伝えます。

- **目的**：この段階で何を達成しようとしたか
- **結果**：何ができるようになったか、どう確認できるか
- **判断と理由**：設計上の選択、検討した代替案、選ばなかった理由
- **読みどころ**：理解のために読むべきファイルと、そこで使われている考え方
- **残った課題**：未解決の点、次の段階への申し送り

**コードコメント**

「何をしているか」ではなく「なぜそうしたか」を書きます。コードを読めば分かることは書きません。

## 8. 公開とセキュリティ

ソースコードもサイトも、インターネット上の誰もが見られる状態で公開します。コミット履歴、PR、CIのログも公開される前提で、セキュリティには細心の注意を払ってください。利便性と安全性がぶつかる場合は安全性を優先し、判断に迷う場合は作業を止めて相談します。

**リポジトリに入れないもの**

- トークン、APIキー、パスワード、`.env` ファイル。このプロジェクトに秘密情報は1つも必要ない。必要に見えたら設計を疑い、相談する
- 個人情報。メールアドレス、本名、ユーザー名を含むローカルのファイルパス、端末固有の設定
- エディタやOSが作る不要ファイル、ビルド成果物。最初のコミットで `.gitignore` を整える

一度プッシュした内容は、後から消しても履歴に残ります。誤って入れたと気づいたら、自分で履歴を書き換えず、すぐに人間へ報告してください。

**依存パッケージ**

- 数を最小限にする。追加は事前承認（3章）
- 広く使われ保守されているものだけを使い、パッケージ名の綴りを確認する
- ロックファイルをコミットし、CIでは `npm ci` を使う
- 各段階のPR前に `npm audit` を実行し、結果をPRに書く

**GitHub Actions**

- ワークフローごとに `permissions` を明記し、必要最小限にする
- 使うアクションはGitHub公式のものを優先し、バージョンを固定する
- `pull_request_target` を使わない。外部からのPRで権限のある処理が動かないようにする
- デプロイはmainブランチからだけ実行する
- ログに環境変数やパスを不必要に出力しない

**公開するサイト**

- 外部のスクリプト、フォント、画像、CDNを読み込まない
- アクセス解析、広告、Cookieを使わない。利用者の情報を収集・送信しない
- `eval` や、動的な文字列を `innerHTML` に入れる書き方をしない
- Content Security Policyを `meta` タグで設定する。内容は段階3で提案する

**人間が行う設定**

Claude Codeは手順を示すだけにし、設定そのものは人間が行います。段階0で手順を提示してください。

- [ ] コミットに使うメールアドレスを、GitHubが提供する非公開用アドレスにする
- [ ] mainブランチの保護（直接プッシュの禁止、CIの成功を必須にする）
- [ ] シークレットスキャンとプッシュ保護の有効化
- [ ] Dependabotアラートの有効化
- [ ] GitHub Pagesの有効化（段階3）

**PRごとの確認**

各PRの説明に、次の3点を確認した結果を書きます。

1. 差分に秘密情報や個人情報が含まれていない
2. 追加・更新した依存パッケージと、`npm audit` の結果
3. 外部との通信や権限に関わる変更の有無

## 9. 将来の拡張候補

今回は実装しません。4章の設計がこれらを妨げないことだけを確認し、先回りした作り込みはしないでください。

| 候補 | 内容 | 構成への影響 |
| --- | --- | --- |
| カスタム盤面 | サイズと機雷数を自由に指定 | なし。ロジック層は最初から引数で受け取る |
| ベストタイムと統計 | ブラウザ内に記録を保存 | 保存用のモジュールを追加 |
| 推測なしモード | 運に頼らず解ける盤面だけを生成 | 盤面生成を差し替え可能にする |
| スマホ対応 | 長押しで旗、画面幅への追従 | 描画層のみ |
| オンラインランキング | タイムを他の人と競う | サーバーが必要。静的サイトの前提が変わる |
| 別のブラウザアプリ | 同じ進め方で別のアプリを作る | 規約、CI、文書の型をそのまま使い回す |

最後の行のために、規約とCIの設定はマインスイーパー固有の内容を含まない形で書いてください。
