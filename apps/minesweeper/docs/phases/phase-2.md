# 段階2 レポート：画面

## 目的

昔のWindows風の画面とマウス操作を作り、ローカルで遊べる状態にすることです。あわせて、画面を実際のブラウザで確かめる自動テストを入れました。公開（デプロイ）は段階3で行います。

## 結果

`npm run dev -w minesweeper` で起動し、ブラウザで遊べます。

- 難易度3種類（初級 9×9・機雷10、中級 16×16・機雷40、上級 30×16・機雷99）を、盤面の上のボタンで切り替えられる
- 左クリックで開く、右クリックで旗、両クリックと中クリックで周囲をまとめて開く
- 残り機雷数とタイマーを、7セグメント風の表示器で見せる。タイマーは最初のマスを開いた時に始まり、999で止まる
- 顔のボタンでやり直せる。勝ち負けは顔の表情で分かる
- 負けたときは、全機雷、爆発した機雷（赤い背景）、誤った旗（機雷に×）を見せる

確認した結果は次のとおりです。Node.js 26.13.1（Windows）で実行しました。

| コマンド               | 結果                                                              |
| ---------------------- | ----------------------------------------------------------------- |
| `npm run format:check` | 成功                                                              |
| `npm run lint`         | 成功                                                              |
| `npm run typecheck`    | 成功                                                              |
| `npm test`             | 成功（9ファイル、221件）                                          |
| `npm run build`        | 成功                                                              |
| `npm run test:browser` | 成功（54件 × Chromium、Firefox、WebKit の3種類 = 162件。約2分半） |

このほかに、Claude Code本体がChromiumでスクリーンショットを撮り、初級のプレイ中、負けたあと、上級の盤面に表示の崩れがないことを目で確かめました。

確認していないことは次のとおりです。

- **実際に手で遊んだときの手触り**。マウスの操作はすべて自動操作で確かめたもので、人が遊んではいません。**ここは人間に確認していただきたい点です**
- macOSでの動作、およびChrome、Edge、Safariそのものでの動作。テストに使ったのは、Playwrightが用意する3種類のエンジン（Chromium、Firefox、WebKit）のWindows版です。SafariはWebKitで代用しています
- CI（GitHub Actions、Linux）でのブラウザテスト。PRを作成した時点で初めて動きます
- スクリーンリーダーでの読み上げ
- 勝ったときの顔、旗の絵、マイナスのカウンターの見た目。属性の値はテストで確かめていますが、絵そのものは目で見ていません

## 判断と理由

### 要件定義書と食い違う点（人間の判断による変更）

| 要件定義書                              | 実際                                                       | 経緯                                                                                             |
| --------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 3章「画面の自動テストは不要」           | Playwrightで、実際のブラウザを操作するテストを入れた       | 人間が最終判断をするまでの品質の確認を、できるだけ自動化したい、という所有者の判断（2026-11-14） |
| 2章の操作は、左クリックと右クリックだけ | 両クリックと中クリックで、数字のマスの周囲をまとめて開ける | 段階1のレビュー（PR #2）で機能の採用が決まり、段階2の計画で操作の割り当てを決めた                |

ロジック層の単体テストをブラウザなしで行う方針は、変えていません。規約（3章「テスト」）は、この段階の最初のコミットで書き換えました。

### 計画の段階で人間が決めたこと

| 論点             | 決定                                                           |
| ---------------- | -------------------------------------------------------------- |
| 周囲を開く操作   | 両クリックと中クリック                                         |
| 難易度の切り替え | 盤面の上にボタン3つ                                            |
| 勝ち負けの表示   | 顔のボタンの表情だけ（画面に見えない通知領域に、文言も入れる） |
| ブラウザテスト   | 3種類のブラウザで、PRごとにCIでも実行する                      |
| 追加する依存     | `@playwright/test`（開発用）と、テスト用ブラウザ本体の取得     |

### Claude Codeが決めたこと

計画で示し、承認を受けたものです。

- **マスは1辺24px**。昔のWindows版の16pxは、今の画面では小さすぎるためです。上級の盤面は幅が約740pxになります。画面のほうが狭いときは、横にスクロールします
- **タイマーは000から始まり、最初のマスを開いて1秒後に001になる**
- **顔は、黄色い丸に目と口の、ごく一般的な絵を自作した**。勝ったときは、サングラスではなく、目を細めて笑う顔にしました。既存の製品の絵に寄せないためです
- **OSのウィンドウを模したタイトルバーは付けない**
- **キーボード操作と「？」マークは作らない**。要件にないためです
- **スクリーンショットを照合するテストは入れない**。OSやブラウザの版で結果が揺れやすいためです。見た目は人間がレビューで確認します

実装の途中で決めたものです。

- **左ボタンは「離したとき」に開き、右ボタンは「押したとき」に旗を切り替える**。昔のWindows版に合わせました。左ボタンを押したままポインタを動かすと、離した位置のマスが開きます
- **右→左の順に押した両クリックでは、最初の右押下で旗が切り替わる**。開いた数字のマスの上では旗は立たないので、周囲を開く操作としては問題になりません。閉じたマスの上で行うと、旗が切り替わります
- **盤面の外で押して、マスの上で離しても、開かない**。押下は盤面の中だけで受けているためです。中ボタンだけは押した場所を見ておらず、マスの上で離せば周囲を開きます
- **盤面の外で左ボタンを押したまま、マスの上で右ボタンを押しても、旗は立たない**。左を押している最中の右押下は、左をどこで押したかに関係なく、両クリックの始まりとして扱っているためです。このあとどちらかを離すと、周囲を開く操作になります。状態機械の単体テストで確かめています。ブラウザテストにはありません
- **フォントは、名前を指定せず、端末の標準のものに任せる**（`sans-serif`、`system-ui`）。フォントのファイルは読み込みません。最初の実装は数字に `Verdana`、`Arial` を名指ししていましたが、要件定義書4章の「既存製品のフォントは使わない」との関係が紛らわしいので、レビュー用エージェントの指摘を受けて外しました
- **ウィンドウの外でボタンを離された場合に備え、毎回「いま押されているボタン」と突き合わせる**。状態が残って、次の操作で意図しないマスが開くのを防ぐためです
- **タイマーの表示は0.1秒ごとに更新する**。表示する値は開始時刻との差から求めるので、更新の間隔は値の正しさに影響しません
- **ページの背景は青みがかった灰色、パネルの下に操作の説明を1行置いた**

### ブラウザテストの作り

- **ビルドした成果物を確かめる**。開発サーバーではなく、公開するものと同じファイルを `vite preview` で配信して操作します
- **機雷の位置は、乱数を差し替えて固定する**。ページの読み込み前に `Math.random` を種つきの乱数に差し替え、テストの側でも同じ乱数でロジック層の配置関数を呼んで位置を求めます。本番のコードに、テスト専用の入口（特別なURLや変数）はありません
- **盤面の期待値は、本番のロジックを呼ばずに求める**。数字や空白の広がりを、テストの側で機雷の位置から計算し直しています。本番と同じ関数で期待値を作ると、ロジックの誤りが期待値にも写ってしまうためです
- **タイマーは、Playwrightの時計を進める機能で確かめる**。999秒を実際に待つ必要がありません
- **失敗したテストを自動でやり直さない**。やり直しで成功に変わると、不安定なテストに気づけないためです
- **テスト用サーバーのアドレスは `127.0.0.1` に固定した**。最初は `localhost` と書いており、Firefoxで1件だけ接続に失敗することがありました（3回のうち1回）。固定したあとは、2回続けて全件成功しています

### 実装の進め方

仕様と、画面の要素に付ける目印（`data-testid` など）をClaude Code本体が決め、実装とブラウザテストを別々のサブエージェントに委譲しました。テストを書く担当には実装を直すことを禁じ、仕様と食い違いがあれば報告させる形にしています（食い違いの報告はありませんでした）。本体は次のレビューをしました。

- コードの通読。`any`、`as`、`!`、Lintの無効化、`innerHTML`、インラインのスクリプトやstyle属性がないことの確認
- すべての検査の再実行。ブラウザテストは3回実行し、不安定な1件の原因を直した
- スクリーンショットでの見た目の確認
- テストが誤りを検知できることの確認（テストの担当が実施）。本番のコードをわざと3通りに壊し、該当するテストが失敗することを見たうえで、元に戻しています

| 壊し方                                             | 検知したテスト            |
| -------------------------------------------------- | ------------------------- |
| 右クリックのメニューを止める処理を外す             | 右クリックのメニューの2件 |
| タイマーの上限を99にする                           | 999で止まることのテスト   |
| 両クリックのあと、残った片方を離すと開くようにする | 両クリックのテスト4件     |

### 計画からの変更

- 描画層のファイルが、計画より3つ多くなりました（`difficulty-bar.ts`、`seven-segment.ts`、`svg.ts`）。DOMを組み立てる部分を部品ごとに分けたためです
- テストの `test.only` は、手元でも使えない設定にしました（消し忘れたままCIが成功するのを防ぐため）。一部だけ実行したいときは `--grep` を使います

## 読みどころ

1. **まず遊んでみてください**。`npm run dev -w minesweeper`。手触りと見た目は、人間にしか判断できません
2. `docs/architecture.md` の「描画層の作り」：全体の流れと、マウス操作の表
3. `src/ui/app.ts`：部品をつなぐ中心。`applyState`（状態が変わったときの処理）から読むと流れが追えます
4. `src/ui/mouse-input.ts`：ボタンの押下・解放の列を、操作に変換する状態機械。**いちばん込み入っているところです**。`tests/ui/mouse-input.test.ts` のテスト名を読むと、どの列がどの操作になるかが一覧できます
5. `src/ui/board-view.ts`：盤面の描画。`getCellView` の結果だけで描いています
6. `index.html`：自作の絵（SVG）の定義
7. `tests/browser/helpers.ts` の前半：機雷の位置を固定する仕組み（`createSeededRandom`、`MineOracle`、`openSeededPage`）
8. `tests/browser/play.spec.ts`：テスト名を上から読むと、画面の動作の一覧になります

## 残った課題

- **複数の機雷を同時に開いたときの見せ方**（段階1からの持ち越し）。誤った旗で周囲を開くと、爆発した機雷として赤く見せるのは1つだけ（最も左上のもの）です。画面で見て、違和感がないか判断してください
- **ブラウザテストの所要時間**。手元で約2分半です。大半はFirefoxで、テスト1件ごとの起動に時間がかかっています。CIではブラウザ本体の取得も加わります。長すぎる場合は、CIではChromiumだけにする、などの調整ができます
- **テストが検知できない誤り**
  - タイマーの上限を999より大きくする誤り。表示の側でも999に丸めているので、画面に違いが出ません（上限そのものは単体テストで確かめています）
  - 左ボタンを押したまま別のマスへ動かして離す操作、盤面の外で離す操作、ウィンドウが裏に回った場合。ブラウザテストでは確かめていません（状態機械の単体テストで、ボタンの状態の食い違いは確かめています）
- **`npm audit` の中程度の警告7件は、段階0から変わっていません**（`typescript-eslint` が内部で使う `minimatch`。更新を待つと決定済み）。今回追加した `@playwright/test` に由来する警告はありません
- **段階3への申し送り**
  - CSPの案を作るときの前提：スクリプトとスタイルはすべて自サイトのファイルで、インラインのスクリプトとstyle属性はありません。絵はHTMLに埋め込んだSVGです。JavaScriptからCSSの変数を1つ設定しています（盤面の列数）。CSPがこれを妨げないことを、ブラウザテストで確かめる必要があります
  - 外部への通信が発生しないことは、ブラウザテスト（`page.spec.ts`）で確かめています
