# 段階1 レポート：ゲームロジック

## 目的

マインスイーパーのルールを、画面なしで動くコードとして実装し、単体テストで正しさを確かめることです。画面は作っていません。

## 結果

`apps/minesweeper/src/logic/` に、次のことができるコードが入りました。

- 盤面の大きさと機雷数を指定してゲームを作る
- マスを開く。機雷のないマスが連続する部分は自動で開く
- 旗を立てる・外す。残り機雷数を求める
- 最初に開くマスには機雷を置かない
- 勝ち負けを判定する。負けたときに、全機雷と誤って立てた旗を区別して見せられる

確認した結果は次のとおりです。Node.js 26.13.1（Windows）で実行しました。

| コマンド               | 結果                     |
| ---------------------- | ------------------------ |
| `npm run format:check` | 成功                     |
| `npm run lint`         | 成功                     |
| `npm run typecheck`    | 成功                     |
| `npm test`             | 成功（5ファイル、121件） |
| `npm run build`        | 成功                     |

確認していないことは次のとおりです。

- macOSでの動作
- 実際に遊んだときの手触り。画面がないので、ルールが期待どおりかはテストでしか確かめていません。段階2で遊べるようになってから、改めて見ていただく必要があります

## 判断と理由

### ルールの解釈

計画の時点で確認し、すべて昔のWindows版に合わせる形で承認を受けました。

| 論点                                                 | 採用した動作                                                           |
| ---------------------------------------------------- | ---------------------------------------------------------------------- |
| 最初のマスの安全の範囲                               | 開いたマス1つだけ。周囲8マスには機雷がありうる                         |
| 旗の数の上限                                         | なし。機雷数を超えると、残り機雷数はマイナスになる                     |
| 勝ったとき                                           | 残りの機雷すべてに自動で旗が立ち、残り機雷数が0になる                  |
| 空白の広がりが旗に当たったとき                       | 旗のマスは開かず、旗を通り抜けもしない                                 |
| 最初のマスを開く前の旗                               | 立てられる。ゲームは始まらない（タイマーは最初のマスを開いた時点から） |
| 盤面の外の位置、不正な設定                           | エラーを投げる                                                         |
| 終了後の操作、開いたマスへの操作、旗のマスを開く操作 | 何もせず、同じ状態を返す                                               |

「基本動作は昔のWindows版に合わせる」という指示は、上のように判断が分かれる動作を昔のWindows版に寄せる、という意味で受け取りました。昔のWindows版にあっても要件定義書にない操作（数字のマスを両クリックして周囲を開く、「？」マーク）は実装していません。

### 状態を書き換えず、新しい状態を返す

- **選んだ案**：`openCell(state, …)` のような関数が、新しい状態を返す。渡された状態は変えない
- **選ばなかった案**：内部の状態を書き換えるクラス。操作の前後を比べるテストが書きにくく、描画層が「いつ変わったか」を知る仕組みも別に必要になります
- **気になる点**：操作のたびにマスの配列を作り直します。上級でも480マスなので、問題にならないと判断しました

### 機雷の配置を引数で渡す

要件は「乱数を外から注入できること」です。乱数そのものではなく、乱数から作った「配置する関数」を `openCell` に渡す形にしました。

- テストでは、決まった位置を返す関数を渡すだけで盤面を固定できます。乱数の値から配置を逆算する必要がありません
- 将来の「推測なしモード」は、別の配置関数を渡すだけで実現できます（9章）
- 配置関数を毎回の `openCell` に渡すのは少し冗長です。状態の中に関数を持たせる案もありましたが、状態を単純なデータだけに保つことを優先しました

### 見せ方の変換をロジック層に置く

「負けたら全機雷と誤った旗を表示する」はゲームのルールなので、`getCellView` としてロジック層に置きました。描画層にこの判断を書くと、要件の「ゲームのルールを描画層に書かない」に反します。

### タイマーと難易度はこの段階に含めない

- タイマーは時計に触れるので、ロジック層には置けません。上限999の扱いも含めて段階2で作ります
- 難易度3種類は、要件に従ってロジック層に埋め込んでいません。テストでは3種類の大きさを使っていますが、定義は段階2で描画層の側に置きます

### 実装の進め方

型と関数の仕様をClaude Code本体が決め、実装とテストを2つのサブエージェントに分けて委譲しました（機雷の配置／ゲーム本体と見せ方の変換）。戻ってきたものに対して、本体が次のレビューをしています。

- コードとテストの通読。規約の違反（`any`、`as`、`!`、Lintの無効化）がないことの確認
- 2つのモジュールを組み合わせたテストの追加（`integration.test.ts`）。実装とは別の書き方で盤面の整合性を確かめます
- ゲーム本体をわざと6通りに壊し、テストがすべて検知することの確認（確認後は元に戻しています）

### 計画からの変更

- コミットは、計画では「開く」「旗」「勝敗判定」を分ける予定でしたが、1つのファイル（`game.ts`）にまとまったため、1コミットにしました
- 計画になかった `integration.test.ts` を追加しました
- 機雷の配置関数に、計画より多くの入力チェックが入っています（最初のマスの添字が盤面の外、乱数がNaNを返す、など）

## 読みどころ

1. `src/logic/types.ts`：データの持ち方の全体。**ここがいちばん判断していただきたいところです**
2. `docs/architecture.md` の「ロジック層の作り」：関数の一覧と、進行状況の移り変わり
3. `src/logic/game.ts`：ルールの本体。`openCell` → `layMines`（配置）→ `floodOpen`（空白の広がり）の順に読むと流れが追えます
4. `src/logic/game.test.ts`：盤面を文字で書いたテスト。`*` が機雷、`#` が閉じたマスです。ルールの解釈が期待どおりかを、ここで確かめられます
5. `src/logic/cell-view.ts`：負けたときの見せ方。25行です
6. `src/logic/mine-placement.ts`：シャッフルを途中で打ち切って機雷の位置を選ぶ方法
7. `src/logic/integration.test.ts`：乱数の配置と組み合わせて、どの盤面でも成り立つ性質を確かめるテスト

## 残った課題

- **`npm audit` の中程度の警告7件は、段階0から変わっていません**。`typescript-eslint` が内部で使う `minimatch` に由来し、公開するサイトには含まれません。依存パッケージの追加・更新はありません
- **段階2への申し送り**
  - 難易度3種類の定義、タイマー（上限999）、残り機雷数の表示（マイナスの見せ方）は描画層で作ります
  - 描画層は `logic/index.ts` が公開するものだけを使います
  - 本番の配置関数は `createRandomMinePlacer(Math.random)` で作ります
- **提案（実装していません）**：数字のマスを両クリックして周囲をまとめて開く操作は、昔のWindows版にあり、遊びやすさへの影響が大きい機能です。要件定義書の範囲外なので入れていませんが、追加する場合はロジック層に関数を1つ足す形になります
