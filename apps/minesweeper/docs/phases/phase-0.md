# 段階0 レポート：土台

## 目的

ゲームを作り始める前に、開発の道具と決まりごとを整えることです。具体的には次の3つを用意しました。

- TypeScript、Vite、Vitest、ESLint、Prettierが動く雛形
- PRのたびにチェックを自動で実行するCI
- 規約、設計、進め方を書いた文書

ゲームのコードは1行も書いていません。

## 結果

次のコマンドがすべて成功する状態になりました。Node.js 26.13.1（Windows）で確認しています。

| コマンド               | 結果                                    |
| ---------------------- | --------------------------------------- |
| `npm ci`               | 成功                                    |
| `npm run format:check` | 成功                                    |
| `npm run lint`         | 成功                                    |
| `npm run typecheck`    | 成功                                    |
| `npm test`             | 成功（テスト1件）                       |
| `npm run build`        | 成功（`apps/minesweeper/dist/` に出力） |

確認していないことは次のとおりです。

- macOSでの動作。Windowsでしか実行していません
- `npm run dev -w minesweeper` で開いたページをブラウザで見ること。ビルドが通ることだけ確認しました。表示されるのは「マインスイーパー（準備中）」という文字だけのページです
- Claude Codeのフックが、実際の作業中に確認を求めること。検査スクリプトに入力を直接渡す形では動作を確認しましたが、フックの設定はClaude Codeの再起動後に読み込まれるため、作業中の発動は未確認です

## 判断と理由

### 複数のアプリを1つのリポジトリに入れる

要件定義書の9章にある「別のブラウザアプリ」を同じリポジトリに足していく方針になったため、アプリを `apps/<アプリ名>/` に置き、npm workspacesでまとめました。

- **選んだ案**：npm workspaces。ロックファイルと `npm audit` が1つで済み、TypeScript、ESLint、Prettierの設定を全アプリで共有できます
- **選ばなかった案**：アプリごとに独立した `package.json` とロックファイルを持つ。アプリ同士の影響はなくなりますが、依存の管理とCIがアプリの数だけ増えます

### 要件定義書との食い違い

次の2点は、人間の承認を得て要件定義書と違う形にしています。

| 要件定義書                                                            | 実際                                           | 理由                                     |
| --------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------- |
| `docs/requirements.md`、`docs/architecture.md`、`docs/phases/`（7章） | `apps/minesweeper/docs/` の下                  | アプリ固有の文書をアプリごとに分けるため |
| mainへの直接コミットをしない（5章）                                   | `.gitignore` だけの初期コミットをmainに1つ作成 | 空のリポジトリではPRを出せないため       |

要件定義書の写しは、原本の3行目にあった氏名を除いています（8章の「本名を入れない」に従うため）。それ以外は原本と同じです。

### 依存パッケージ

すべて開発用で、実行時に読み込むライブラリは0個です。

| パッケージ               | 用途                         | 3章の表          |
| ------------------------ | ---------------------------- | ---------------- |
| `typescript`             | 型チェック                   | あり             |
| `vite`                   | 開発サーバーとビルド         | あり             |
| `vitest`                 | テスト                       | あり             |
| `eslint`                 | 静的解析                     | あり             |
| `prettier`               | 整形                         | あり             |
| `@eslint/js`             | ESLintの標準ルール集         | なし（承認済み） |
| `typescript-eslint`      | ESLintでTypeScriptを扱う     | なし（承認済み） |
| `eslint-config-prettier` | ESLintとPrettierの衝突を防ぐ | なし（承認済み） |

### ロジック層の制約をESLintで検査する

`src/logic/` でDOMやタイマーを使ったり、描画層を読み込んだりすると、ESLintがエラーにします。規約を文章で書くだけでなく、違反したときに機械的に気づけるようにするためです。当初の計画にはなかった追加です。

### GitHub ActionsのアクションをコミットSHAで固定する

`@v7` のようなタグは、後から別の内容に付け替えることができます。SHAで固定すれば、確認した時点の内容だけが実行されます。代わりに、アクションの更新は手作業になります。

### テストはブラウザ環境を模擬しない

Vitestの実行環境を `node` にしました。ロジック層が誤ってDOMに触れると、テストが失敗して気づけます。段階0のテスト1件は、この設定が効いていることだけを確かめています。

### Claude Codeの安全装置を追加した

段階0の作業中に、整形コマンド（`prettier --write .`）が、リポジトリのフォルダに置かれていた要件定義書の原本まで書き換える事故がありました。表の空白がそろえられただけで、元に戻してファイルサイズが一致することを確認しましたが、人間が書いたファイルを意図せず変更したことに変わりはありません。

再発を防ぐため、次の2つを追加しました。

- 規約の8章「作業の安全装置」。一括書き換えの前に対象を確認する手順
- Claude Codeのフック（`.claude/settings.json`、`.claude/hooks/guard.mjs`）。要件定義書の編集、未追跡ファイルがある状態での一括書き換え、承認の必要な操作を検知して、実行前に人間へ確認します

フックはコマンドの文字列を照合するだけなので、すり抜けはありえます。手順を守ることの代わりにはなりません。

### コミットの分け方

依存パッケージは一度にインストールしたため、`package.json`、ロックファイル、各ツールの設定、アプリの雛形を1つのコミットにまとめました。ツールごとに分けると、途中のコミットでロックファイルと `package.json` が合わなくなるためです。

## 読みどころ

読む順番のおすすめです。

1. `docs/conventions.md`：規約の全体。**このPRでいちばん判断していただきたい文書です**
2. `README.md` と `CLAUDE.md`：リポジトリの構成と、コマンドの一覧
3. `apps/minesweeper/docs/architecture.md`：ロジック層と描画層の分け方
4. `package.json`（ルート）と `apps/minesweeper/package.json`：workspacesの仕組み。ルートのスクリプトが、各アプリの同名のスクリプトを順に呼びます
5. `eslint.config.js`：ロジック層の制約を検査している部分
6. `.github/workflows/ci.yml`：CIの内容。`permissions` とアクションの固定のしかた
7. `.claude/hooks/guard.mjs`：安全装置の検査内容
8. `docs/github-setup.md`：人間が行う設定の手順

## 残った課題

- **`npm audit` で中程度の警告が7件あります**。すべて、`typescript-eslint` が内部で使う `minimatch` の1件（GHSA-g3hv-75wg-m249、細工されたパターンで処理が重くなる問題）に由来します。Lintのときだけ動く開発用パッケージで、公開するサイトには含まれません。`npm audit fix --force` は `typescript-eslint` を古い版に戻すだけなので、実行していません。`typescript-eslint` の更新を待つか、`overrides` で `minimatch` の版を上げるかは、人間の判断をお願いします
- **人間が行う設定が残っています**。`docs/github-setup.md` の2〜5（mainブランチの保護、シークレットスキャン、Dependabotアラート、Actionsの権限の確認）です。ブランチの保護は、このPRでCIが1回動いたあとに設定できます
- **要件定義書の原本がリポジトリのフォルダに残っています**。Gitの管理対象からは外してありますが、写しが `apps/minesweeper/docs/` にあるので、原本はフォルダの外へ移すことをおすすめします
- **GitHub Pagesの公開URL**は `https://<ユーザー名>.github.io/browser-apps/minesweeper/` の形になります。サイトのトップにアプリの一覧ページを置くかどうかは、段階3の計画で相談します
- **macOSでの確認**は、macOSの端末で `npm ci` と各チェックを実行したときに行ってください
