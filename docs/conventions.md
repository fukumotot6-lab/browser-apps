# 規約

このリポジトリのすべてのアプリに共通する規約です。規約の本文はこのファイルだけに書き、ほかの文書からは参照します。

アプリごとの要件定義書と食い違う場合は、要件定義書を優先し、食い違いを人間に報告します。規約を変えるときは、コードより先にこの文書を直します。

## 1. 判断の優先順位

1. 人間が理解し、判断できること
2. 安全であること
3. 単純であること
4. 機能が多いこと

文書に書かれていない判断が必要になったら、推測で進めずに質問します。

## 2. リポジトリの構成

- アプリは `apps/<アプリ名>/` に1つずつ置き、npm workspacesでまとめる
- 全アプリ共通の設定（TypeScript、ESLint、Prettier、CI）と開発用パッケージはリポジトリのルートに置く
- アプリ固有の文書は `apps/<アプリ名>/docs/` に置く。要件定義書が `docs/...` と書いている文書は、この場所に読み替える
- 全アプリ共通の文書は `docs/` に置く

## 3. コーディング

### TypeScript

- `strict` を有効にする。`any` は使わない。型が分からない値は `unknown` で受けて絞り込む
- 型アサーション（`as`）と非nullアサーション（`!`）は、ほかに書きようがない場合に限り、理由をコメントに書く
- Lintの警告を無効化コメントで消さない。どうしても必要な場合は、対象の行だけを無効化し、理由を書く
- `eval`、および動的な文字列を `innerHTML` に入れる書き方をしない

### 命名

| 対象                               | 書き方           | 例                   |
| ---------------------------------- | ---------------- | -------------------- |
| ファイル、ディレクトリ             | kebab-case       | `game-state.ts`      |
| 変数、関数                         | camelCase        | `openCell`           |
| 型、インターフェース、クラス       | PascalCase       | `GameState`          |
| モジュールの外に公開する不変の定数 | UPPER_SNAKE_CASE | `MAX_SECONDS`        |
| 単体テストのファイル               | `<対象>.test.ts` | `game-state.test.ts` |
| ブラウザテストのファイル           | `<対象>.spec.ts` | `play.spec.ts`       |

- 名前は英語で書く。真偽値は `is`、`has`、`can` で始める
- エクスポートは名前付きにする。設定ファイルなど、ツールが既定エクスポートを要求する場合だけ例外とする

### 層の分離

アプリのコードは、ロジック層（`src/logic/`）と描画層（`src/ui/`）に分けます。

- ロジック層はDOM、`window`、タイマーに触れず、描画層を読み込まない。Node.js上で単体テストできる状態を保つ
- 乱数や現在時刻のように実行のたびに変わるものは、ロジック層の外から渡す
- 描画層は、ロジック層の状態を画面に反映し、利用者の操作をロジック層の呼び出しに変換するだけにする。アプリのルールを描画層に書かない

ロジック層の制約の一部はESLintで検査します（`eslint.config.js`）。

### コメント

- 「何をしているか」ではなく「なぜそうしたか」を書く。コードを読めば分かることは書かない
- コメントと文書は日本語で書く

### テスト

- ロジック層と、描画層のうちDOMに触れない関数は、Vitestの単体テストで確かめる。Vitestではブラウザ環境を模擬しない
- 描画層のうちDOMに触れる部分は、Playwrightで実際のブラウザを操作するテスト（ブラウザテスト）で確かめる。見た目の良し悪しは自動では判定せず、人間がレビューで確認する
- テストファイルは実装と分け、アプリの `tests/` に置く。単体テストは `src/` と同じ構成にして、対象のファイルを探しやすくする（例：`src/logic/game.ts` のテストは `tests/logic/game.test.ts`）
- ブラウザテストは `tests/browser/` に置き、ファイル名を `<対象>.spec.ts` にする。Vitestが拾わないようにするため
- ブラウザテストのために、本番のコードにテスト専用の入口を作らない
- テスト名は、確かめている振る舞いが分かる日本語の文にする
- 乱数に依存する処理は、値を固定して結果を再現できるようにする

### 整形と静的解析

- 整形はPrettier、静的解析はESLintに任せ、手作業で書式を議論しない
- コミット前に `npm run format:check`、`npm run lint`、`npm run typecheck`、`npm test`、`npm run build` が通ることを確認する。描画層を変えたときは `npm run test:browser` も確認する

## 4. Git運用

### ブランチ

- 最新の `main` から、要件定義書が定める名前で切る
- 1ブランチには1段階の変更だけを入れる
- 段階に属さない小さな変更（規約や進め方の変更など）は、`<コミットの種類>/<内容を表す短い英語>` の名前で切る（例：`docs/approval-policy`）。1ブランチには1つの目的の変更だけを入れる
- `main` への直接コミット、PRのマージ、強制プッシュは、人間の承認なしに行わない。マージは人間が行う

### コミット

- 1コミットは「ひとことで説明できる1つの変更」にする
- 設定の変更、実装、リファクタリング、文書の更新を同じコミットに混ぜない。実装とそのテストは同じコミットに入れる
- 各コミットの時点で、ビルドとテストが通る状態を保つ
- 「作業中」「修正」のような、内容の分からないコミットを残さない

メッセージの書式は次のとおりです。

```
<種類>(<範囲>): <変更の要約>

<理由や背景。自明でない場合に書く>
```

- 種類は次から選ぶ

  | 種類       | 使う場面                       |
  | ---------- | ------------------------------ |
  | `feat`     | 機能の追加、変更               |
  | `fix`      | 不具合の修正                   |
  | `refactor` | 振る舞いを変えないコードの整理 |
  | `test`     | テストだけの追加、修正         |
  | `docs`     | 文書の追加、更新               |
  | `chore`    | 設定、依存パッケージ、雛形     |
  | `ci`       | GitHub Actionsのワークフロー   |

- 範囲はアプリ名（例：`minesweeper`）。リポジトリ全体に関わる変更では省略する
- 要約は日本語で、何を変えたかを書く。本文には、なぜそうしたかを書く

### PR

- 1段階につき1本出す。段階に属さない小さな変更は、1つの目的につき1本出す
- 説明文は `.github/pull_request_template.md` の項目をすべて埋める
- 人間がPRに付けたコメントに対応したときは、そのコメントへの返信として、何をしたかと、対応するコミットを書く
- PRに修正をプッシュしたときは、説明文を実際の内容に合わせて直す

### レビュー用エージェントによるレビュー

人間のレビューの前に、実装した担当とは別のレビュー用エージェントが、PRを1本ずつレビューします。人間が最終判断をするまでの品質の確認を、できるだけ自動で済ませるためです。人間のレビューの代わりにはなりません。

これは、アプリの要件定義書が定める流れ（PRを作成して作業を止める → 人間がレビューする）の間に、手順を1つ足すものです。リポジトリの所有者の指示で追加しました。

**いつ実行するか**

- PRを作成したときと、PRにコミットをプッシュしたとき。説明文やコメントだけを直したときは実行しない
- 説明文を実際の内容に合わせてから、レビューを実行する

**レビュー用エージェントがすること**

- 定義は `.claude/agents/pr-reviewer.md` にある。実装のやり取りは渡さず、PRの番号だけを渡す。実装した側の説明に引きずられない判断をさせるため
- 追跡対象のファイルの変更、コミット、プッシュ、マージ、ブランチの切り替え、依存パッケージのインストール、PRの承認をしない。行う書き込みは、総評のコメント1件だけ
- 検査コマンドを実行するのは、このリポジトリ自身のブランチから出たPRに限る。フォークから出たPRは、差分を読むだけにする。PRに含まれるコードを、手元の認証情報がある環境で動かすことになるため
- 総評は、PRのコメントとして残す。判定、指摘（重要度と場所つき）、確かめたこと、確かめていないことを書く
- 2回目以降のレビューでは、前回の総評と、それへの対応のコメントを読む。前回の指摘が直っているかを確かめ、対応しないとされた指摘は、理由に納得できない場合だけ改めて挙げる

これらの制限は、定義に書いた指示によるものです。レビュー用エージェントが使える道具から編集用のものは外していますが、コマンドの実行は止めていないので、仕組みで完全に強制できているわけではありません。

**総評を受けたあと**

1. 実装の担当は、指摘ごとに、対応するかしないかを決める。対応しない指摘は、理由を書く
2. 対応する指摘は、同じブランチで修正する。プッシュの前に人間へ確認するのは、8章のとおり
3. プッシュしたら、指摘ごとの対応をPRのコメントに書き、もう一度レビューを実行する
4. 再レビューは1回までとする。2回目の総評にも重要度が高または中の指摘が残った場合は、それ以上は自動で繰り返さず、人間に判断を求める
5. 総評と対応の内容を人間に報告して、作業を止める

## 5. 依存パッケージ

- 数を最小限にする。追加は、理由を添えて事前に人間の承認を得る
- 広く使われ、保守されているものだけを使う。インストール前にパッケージ名の綴りを確認する
- 開発用パッケージはルートの `package.json` にまとめる。実行時に読み込むライブラリは0個を目標とする
- `package-lock.json` をコミットし、CIでは `npm ci` を使う
- 各段階のPRを出す前に `npm audit` を実行し、結果をPRに書く

## 6. セキュリティ

ソースコード、コミット履歴、PR、CIのログ、公開するサイトは、すべて誰でも見られる前提で扱います。利便性と安全性がぶつかる場合は安全性を優先し、迷ったら作業を止めて相談します。

### リポジトリに入れないもの

- トークン、APIキー、パスワード、`.env` ファイル。秘密情報が必要に見えたら設計を疑い、相談する
- 個人情報。メールアドレス、本名、ユーザー名を含むローカルのファイルパス、端末固有の設定
- エディタやOSが作る不要ファイル、ビルド成果物

誤って入れたと気づいたら、自分で履歴を書き換えず、すぐに人間へ報告します。

### GitHub Actions

- ワークフローごとに `permissions` を明記し、必要最小限にする
- GitHub公式のアクションを優先し、コミットSHAでバージョンを固定する。SHAの横に、対応するバージョンをコメントで書く
- アクションの更新は、Dependabotが作るPR（`.github/dependabot.yml`）で受け取る。CIの結果を確認して、人間がマージする
- `pull_request_target` を使わない
- デプロイは `main` ブランチからだけ実行する
- ログに環境変数やパスを不必要に出力しない

### 公開するサイト

- 外部のスクリプト、フォント、画像、CDNを読み込まない
- アクセス解析、広告、Cookieを使わない。利用者の情報を収集、送信しない
- Content Security Policyを `meta` タグで設定する

### PRごとの確認

各PRの説明に、次の3点を確認した結果を書きます。

1. 差分に秘密情報や個人情報が含まれていない
2. 追加、更新した依存パッケージと、`npm audit` の結果
3. 外部との通信や権限に関わる変更の有無

### 人間が行う設定

リポジトリ設定の変更は、Claude Codeが手順を示し、人間が行います。手順は [github-setup.md](github-setup.md) にあります。

## 7. 文書

- 規約と記録は、リポジトリ内のMarkdownファイルに集約する。会話の中だけで決まったルールを残さない
- 各段階の終わりに、段階レポートを `apps/<アプリ名>/docs/phases/phase-N.md` に書く。作業ログではなく、目的、結果、判断と理由、読みどころ、残った課題を書く

## 8. 作業の安全装置

Claude Codeが、意図しないファイルの書き換えや、承認の必要な操作をしないための決まりです。

### 確認の要る操作と要らない操作

Claude Codeが実行の前に人間へ確認するかどうかは、元に戻せるか、外から見えるかで分けます。

| 操作                                                 | 確認 | 理由                                                                                                  |
| ---------------------------------------------------- | ---- | ----------------------------------------------------------------------------------------------------- |
| 作業中のファイルの編集、置き換え、新規作成           | 不要 | Gitで元に戻せる。毎回の確認は作業の妨げになる                                                         |
| ファイルやディレクトリの削除                         | 必要 | 未追跡のファイルは元に戻せない                                                                        |
| プッシュ、PRの作成                                   | 必要 | 公開され、後から消しても履歴に残る                                                                    |
| 自分のPRへのコメント、コメントへの返信、説明文の修正 | 不要 | 4章で定めた決まった書き込みで、そのPRの中に閉じている。公開はされるので、秘密情報や個人情報を書かない |
| PRの承認、PRを閉じる操作                             | 必要 | 承認とマージの判断は人間が行う                                                                        |
| 4章、5章、6章で承認が必要としている操作              | 必要 | それぞれの章のとおり                                                                                  |

人間がその作業の指示の中で明示した操作（例：「PRの作成まで進めてよい」）は、改めて確認しません。以前の作業で得た承認は、次の作業には持ち越しません。

編集の確認が要らないのは、頼まれた作業の範囲のファイルに限ります。下の手順は変わらず守ります。

### 手順

- 人間が書いたファイルは、頼まれた範囲だけを変更する。整形や置換のついでに書き換えない
- 複数のファイルを一括で書き換えるコマンド（整形、自動修正、一括置換）は、次の順で実行する
  1. 確認用のモード（`npm run format:check` など）で、対象になるファイルの一覧を見る
  2. 一覧に、意図しないファイルやGitで管理していないファイルがないことを確かめる
  3. 新しく作ったファイルは先に `git add` し、書き換えられても元に戻せる状態にする
  4. 実行後に `git status` と `git diff --stat` で、変わったファイルが想定どおりかを確かめる
- 意図しない変更に気づいたら、作業を止め、元に戻したうえで、何が起きたかを人間に報告する

### フックによる検査

上の手順と、承認の必要な操作（4章、5章、6章）の一部は、Claude Codeのフックで機械的に検査します。設定は `.claude/settings.json`、検査の内容は `.claude/hooks/guard.mjs` にあります。

| 検査する操作                                                              | 動作                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------ |
| 要件定義書（原本と写し）の編集                                            | 実行前に人間へ確認する                                 |
| 未追跡ファイルがある状態での一括書き換え                                  | 実行前に人間へ確認する                                 |
| プッシュ（強制プッシュを含む）、PRの作成                                  | 実行前に人間へ確認する                                 |
| ファイルやディレクトリの削除                                              | 実行前に人間へ確認する                                 |
| 履歴の書き換え、変更の破棄                                                | 実行前に人間へ確認する                                 |
| mainブランチでのコミットとプッシュ、マージ                                | 実行前に人間へ確認する                                 |
| PRの承認、PRを閉じる操作                                                  | 実行前に人間へ確認する                                 |
| 依存パッケージの追加・削除・更新、未インストールのパッケージの `npx` 実行 | 実行前に人間へ確認する                                 |
| リポジトリ設定を変える `gh` コマンド                                      | 実行前に人間へ確認する                                 |
| コマンドの実行による要件定義書の変更                                      | 実行後に検知し、実行前の控えの場所を示して作業を止める |

フックはコマンドの文字列を照合するだけなので、すり抜けることがあります。フックがあることを理由に、上の手順を省かないでください。検査の対象を変えるときは、先にこの表を直します。

フックの実行にはNode.jsが必要です。WindowsではGit for Windowsに含まれるBashを使います。
